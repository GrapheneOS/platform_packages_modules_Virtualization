# Trusty pVM

This document describes the concepts used in Trusty pVMs. A Trusty pVM is a
Protected Virtual Machine (pVM) managed by the Android Virtualization Framework
(AVF), running the Trusty OS kernel and any Trusted Applications (TAs) built
into its image. For more information on AVF and pVMs, refer to the
[AVF documentation](../../docs/avf.md) and
[Protected VMs documentation](../../docs/protected_vm.md).

To support the AVF environment, the Trusty OS has been updated with several key
features:

*   **Virtio-vsock over PCI**: Support for the AVF-required virtio-vsock driver
    over PCI for efficient Host to VM communication.
*   **Virtio-vsock over virtio-msg over FF-A**: A specialized communication
    mechanism that allows the Trusty pVM to interact securely with Trustzone
    components via the Firmware Framework for Arm (FF-A). This enables a secure,
    point-to-point communication channel between the pVM and a Secure Partition
    (TEE) in the secure world, facilitated by the hypervisor. This channel is
    resilient to host information disclosure attacks because it uses the FF-A
    protocol, particularly FF-A memory sharing, to ensure that the host kernel
    cannot access the communication buffers. For more details on FF-A, see the
    [FF-A documentation](../../docs/ffa.md).
*   **Device Tree Parsing**: Trusty is capable of parsing the device tree (DT)
    generated by crosvm. This includes the pvmfw-specific memory region that
    contains the DICE chain, which provides a verifiable identity for the pVM.
    For more details on the DICE chain, see the
    [pVM DICE Chain documentation](../../docs/pvm_dice_chain.md).

*   **PSCI interfaces**: Implementation of PSCI (Power State Coordination
    Interface) for CPU on/off management within the VM, allowing the hypervisor
    to manage CPU resources.

*   **ARM TRNG**: Integration with the ARM True Random Number Generator for
    secure cryptographic operations and entropy generation.

## Trusty VM payload

The Trusty pVM payload is generated through a series of Soong build rules. This
process involves compiling the Trusty OS, signing the binary, and packaging it
into a format compatible with the crosvm hypervisor.

### Raw binary generation

The initial step is to compile the Trusty OS from source into a raw binary
format. This is handled by a `genrule` in
`trusty/vendor/google/aosp/scripts/Android.bp`. For the security VM on ARM64,
the relevant rule is `trusty_security_vm_arm64.bin`.

This rule executes a build script (`build_trusty`) that orchestrates the Trusty
build system. The output is a raw binary (`.bin` file) which is not yet signed
or prepared for pvmfw. This binary contains the Trusty kernel and all built-in
Trusted Applications (TAs).

### VM payload preparation

Once the raw binary is generated, it needs to be signed and packaged into a
pvmfw-compatible ELF file. This process is defined in
`packages/modules/Virtualization/guest/trusty/security_vm/vm/Android.bp`, which
serves as an example of how to generate a Trusty AVF payload. A similar process
can be followed to generate other Trusty pVMs.

#### Signing and pvmfw footer addition

The `avb_add_hash_footer` Soong rule named `trusty_security_vm_signed_bin` is
responsible for signing the raw binary and adding a pvmfw footer. This rule
takes the unsigned binary and embeds necessary metadata for pvmfw before
signing. The key arguments are:

*   **`private_key`**: Specifies the key used for signing. In AOSP, this points
    to `:avb_testkey_rsa4096`, which is a test key for development. For
    production devices, `system_ext` VMs are re-signed as part of the release
    process by the `/build/make/tools/releasetools/sign_target_files_apks.py`
    script.

    OEMs delivering a Trusty vendor VM must ensure its payload is properly
    signed. It is recommended to use an OEM vendor-specific key, in which
    case `pvmfw` entry 5 must be provisioned with this vendor key as described in
    the [pvmfw documentation](../../pvmfw/README.md).

*   **`partition_name`**: The name of the partition, which is set to "boot". In
    the context of AVB, this serves as a domain separator for the signature. It
    ensures that a signature for one type of payload cannot be re-used for
    another, even if they are signed with the same key. For pvmfw payloads,
    "boot" is a conventional value.

*   **`salt`**: A fixed, public salt value used in the signing process. It is
    good practice to provide a fixed, public salt value to obtain deterministic
    AVF pVM builds.

*   **`rollback_index`**: Set to the value of the
    `platform_security_patch_timestamp` Soong variable, this prevents
    downgrading the pVM to an older, potentially vulnerable version.

*   **`props`**: A list of properties embedded in the signed image. This
    includes `com.android.virt.cap` and `com.android.virt.name`. The
    `com.android.virt.name` property is particularly important as it is expected
    to uniquely identify the pVM. This is the only AVF-managed configuration
    that is part of the signature, preventing a malicious host from allowing
    Trusty VMs signed by the same key to impersonate each other for DICE-based
    authentication.

#### Final ELF file generation

The signed binary is then converted into a final ELF file that can be loaded by
crosvm. This involves a chain of three Soong rules:

1.  **`cc_genrule` (`security_vm.S`):** This rule takes the signed binary and
    uses the `gen_signed_vm_assembly_file` tool to generate an assembly file
    (`security_vm.S`). This assembly file embeds the signed binary as data.

2.  **`cc_object` (`trusty_security_vm_signed_bin_obj`):** The generated
    assembly file is then compiled into an object file.

3.  **`cc_binary` (`trusty_security_vm_signed`):** Finally, the object file is
    linked into a statically linked ELF executable. This rule uses a custom
    linker script (`trusty_vm_sections.ld`) to ensure the signed binary is
    placed in the correct section of the ELF file.

The resulting ELF file is then installed to the system image using a
`prebuilt_etc` rule named `trusty_security_vm.elf`.

## Launcher and its CLI

The Trusty pVM is launched by the `trusty_security_vm_launcher` binary, located
in `packages/modules/Virtualization/guest/trusty/security_vm/launcher`. This
launcher is a Rust binary responsible for configuring and starting the Trusty
pVM using the virtualization service.

The launcher is typically run as a service during the device boot process,
configured via an `.rc` file. An example can be found in
`packages/modules/Virtualization/guest/trusty/security_vm/launcher/security_vm_launcher-arm64.rc.base`.

The launcher supports the following command-line arguments to configure the VM:

*   `--kernel`: Specifies the path to the signed Trusty pVM payload ELF file.
*   `--protected`: When present, launches the VM as a protected VM (pVM).
*   `--name`: Sets the name of the VM.
*   `--memory-size-mib`: Configures the amount of RAM allocated to the VM in
    MiB.
*   `--rpc-services-config`: Path to a JSON file that defines the RPC services
    to be exposed by the VM. This argument can be provided multiple times.
*   `--cpu-topology`: Defines the CPU topology for the VM (e.g., `one-cpu`,
    `match-host`).
*   `--allow-ffa`: Allows the VM to access the FF-A (Firmware Framework for Arm)
    interface, enabling communication with secure components.
*   `--vm-instance-id`: Provides a path to a file containing the VM's unique
    instance ID.

The `.rc` file for the security VM demonstrates a typical invocation:

```
service trusty_security_vm_launcher /system_ext/bin/trusty_security_vm_launcher \
--name security_vm \
--kernel /system_ext/etc/vm/trusty_vm/trusty_security_vm.elf \
--rpc-services-config /system_ext/etc/vm/trusty_vm/security_vm_rpc_services.json \
--vm-instance-id /system_ext/etc/vm/trusty_vm/security_vm_instance_id \
--memory-size-mib 12 \
--protected \
--allow-ffa
```

The service definition in the `.rc` file also specifies several other important
parameters:

*   `user root`: This sets the user that the launcher service runs as. For VMs
    that require FF-A support (enabled with the `--allow-ffa` flag), the
    launcher must currently run as `root` to grant the necessary `CAP_IPC_OWNER`
    capability to the underlying `crosvm` process. This elevation of privilege
    is a temporary solution and is expected to be refined to a more granular
    permission model in the future (b/431822422). For Trusty pVMs that do not
    require FF-A, the user should be set to `system`.
*   `group system virtualmachine`: This sets the group that the launcher service
    runs as.
*   `capabilities`: This grants specific capabilities to the launcher service.
    The `IPC_OWNER` capability is only required for VMs that use the
    `--allow-ffa` option.
*   `stdio_to_kmsg`: This redirects the standard input and output of the service
    to the kernel log (`kmsg`), which is useful for debugging.

### Instance ID

Trusty pVMs utilize a statically defined 64-byte instance ID to uniquely
identify the VM. This ID is generated during the build process by the
`gen_instance_id_for_vm_with_trusted_hal.py` tool. It is important to note that
the instance ID is always provided by the host (in this case, by the launcher)
and should never be used on its own to make security guarantees. It is one of
many inputs into the DICE chain, which provides a much stronger, verifiable
identity for the pVM.

The tool takes a JSON configuration file as input and produces a binary file
containing the instance ID. The JSON file defines several properties of the VM,
including:

*   `is_vm_persistent`: A boolean indicating whether the VM's state should
    persist across reboots. For the security VM, this is set to `true` to ensure
    that secrets managed by the VM are not lost after a factory reset.
*   `vm_partition`: The partition where the VM is located. System pVMs, which
    are defined under `packages/modules/Virtualization`, use the "system"
    partition. However, OEMs can define their own Trusty pVMs and specify
    "vendor" as the partition. An example of a custom Trusty pVM can be found in
    `device/generic/trusty/custom_vm/memshare_vm`.
*   `vm_primary_uuid`: A unique identifier for the VM.
*   `vm_secondary_uuid`: An optional secondary identifier.

For the security VM, the configuration is defined in
`packages/modules/Virtualization/guest/trusty/security_vm/launcher/security_vm_instance_id_config.json`:

```json
{
    "vm_partition": "system",
    "is_vm_persistent": true,
    "vm_primary_uuid": "6c07e3dc-79e1-45a3-936d-b5d73a978f41"
}
```

This configuration specifies that the security VM is persistent, resides in the
system partition, and has a specific UUID. Persistent VMs are designed to be
booted at least once during factory provisioning to establish a "trust on first
use" for their DICE-derived identity.

### VM Payload Config

The `--kernel` argument of the launcher expects a path to the Trusty image. This
image must be a signed ELF file containing the pvmfw configuration, as described
in the [Trusty VM payload](#trusty-vm-payload) section.

It is important to note that the Trusty image is monolithic. It contains both
the Trusty kernel and all user-space Trusted Applications (TAs). The TAs must be
built into the image because Trusty pVMs do not currently support dynamically
loading TAs at runtime.

### RPC Services Config

The launcher acts as an accessor for AIDL services implemented by the Trusty
pVM. These services are referred to as RPC services because they use the
BinderRpc IPC framework.

When a pVM exposes an AIDL service, the launcher allows host applications to
access it by exposing an `IAccessor` Binder service. The `IAccessor` interface,
defined in `frameworks/native/libs/binder/aidl/android/os/IAccessor.aidl`,
provides a way for clients to get a file descriptor for a connection to the RPC
service inside the VM.

For each RPC service, two configurations are required:

1.  **JSON Configuration**: An entry must be added to a JSON configuration file,
    such as
    `packages/modules/Virtualization/guest/trusty/security_vm/launcher/security_vm_rpc_services.json`.
    This entry maps the `IAccessor` Binder service name to the internal RPC
    service name within the VM.

2.  **.rc File Declaration**: The `IAccessor` instances must also be declared in
    the launcher's `.rc` file. This makes the `IAccessor` services discoverable
    to other processes on the host. For example, in
    `security_vm_launcher-arm64.rc.base`:

    ```
    interface aidl android.os.IAccessor/ICommService/security_vm_keymint
    interface aidl android.os.IAccessor/IGatekeeper/security_vm_gatekeeper
    interface aidl android.os.IAccessor/IProvisioning/security_vm_keymint
    ```

#### RPC Services JSON Config

The JSON configuration file passed to the `--rpc-services-config` argument is an
array of objects, where each object defines a single RPC service. The schema for
each object is as follows:

*   `port`: An integer representing the vsock port number that the service
    listens on within the VM.
*   `accessor_name`: A string that defines the name of the `IAccessor` service
    to be exposed on the host. This name typically follows the format
    `android.os.IAccessor/<AIDL_INTERFACE>/<INSTANCE_NAME>`.
*   `internal_rpc_service_name`: A string that specifies the name of the RPC
    service as it is registered within the Trusty pVM.

Here is an example from `security_vm_rpc_services.json`:

```json
[
  {
    "port": 11,
    "accessor_name": "android.os.IAccessor/ICommService/security_vm_keymint",
    "internal_rpc_service_name": "android.trusty.commservice.ICommService/security_vm_keymint"
  },
  ...
]
```

## Early Boot

Certain Trusty pVMs, such as the security VM, need to start early in the boot
process, before the data partition is mounted. This capability is known as
"early boot" and is only available to system pVMs that are deployed in the
`system_ext` partition.

The early boot mechanism leverages the `early_virtmgr`, which is a limited
version of the virtualization service that runs at the beginning of the boot
process. For more details on `early_virtmgr`, see the
[early_vm.md](../../docs/early_vm.md) documentation.

To enable a pVM to boot early, two things are required:

1.  **Fixed CID**: The VM must be assigned a fixed CID (Context ID) from the
    range reserved for early VMs.
2.  **`early_vms.xml`**: A configuration file named `early_vms.xml` must be
    created to map the fixed CID to the launcher service for the VM. This file
    is then installed to the `/system_ext/etc/avf/` directory, as shown in
    `packages/modules/Virtualization/guest/trusty/common/Android.bp`.
